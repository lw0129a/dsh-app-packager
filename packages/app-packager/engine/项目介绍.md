项目名称：`AppPackager`；中文界面名称：`打包工具`。

> 独立性声明：`AppPackager` 是独立的新项目，不依赖、不读取、不复制、不关联旧打包项目。项目配置、SDK、签名、日志和产物均独立维护在本项目目录内。


> 维护规则：只要修改本项目中的脚本、配置、项目读取方式、权限、依赖、操作流程、产物结构或签名规则，必须同步更新本文件。

## 1. 项目定位

`AppPackager（打包工具）` 是一个运行在 macOS 上的本地离线打包工具，用于把本机已有的 uni-app x 项目打成：

- iOS `IPA`
- Android `APK`
- HarmonyOS `HAP`

核心原则：

- 本仓库不内置业务项目，不上传业务源码。
- 不依赖 Git，不执行 `clone`、`fetch`、`checkout`。
- uni-app 项目在运行时从 `config/projects/*.env` 动态读取。
- 每次构建复制业务项目到隔离工作区，不直接修改业务源码。
- HBuilderX 使用静默编译模式，不把构建项目导入编辑器项目列表。
- 安装包统一归档到 `packages/`，并提供 `latest` 快捷入口。
- SDK、签名、产物、工作区和本地项目配置均不提交到 GitHub。
- 安装包上传作为独立扩展层运行，上传失败不回滚打包结果。

## 1.1 分发方式（npm 包与 DeepSeek Harness 插件）

引擎本身仍是 macOS 上的 bash 工具链；仓库在其之上增加了一层 Node 分发壳，使同一套引擎可以 npm/pnpm 安装并作为 DeepSeek Harness 插件在插件市场安装使用。**引擎脚本、配置格式、命令行参数、目录结构与产物规则均未改变**，Node 层只负责交付引擎与转发命令。

- 仓库结构（pnpm monorepo）：
  - `packages/app-packager` → npm 包 `app-packager`（CLI `app-packager`，零运行时依赖）。包内 `engine/` 就是本项目的引擎文件（`打包工具.command`、`初始化.command`、`lib/`、`config/`、`signing/` 等）。
  - `packages/dsh-app-packager` → npm 包 `dsh-app-packager`（DeepSeek Harness 宿主插件，注册 `app_packager_list`、`app_packager_doctor`、`app_packager_check`、`app_packager_build` 四个工具），并带一个浏览器侧面板（`client.js`）：在装了 Web 界面的 Harness 里以「应用打包」入口出现在侧栏面板列表，页面开在中栏，可视化引擎状态、环境检查、项目列表与 check/build 任务的实时日志。面板的宿主侧（`web.js`）只调用同一套 Node 函数与引擎命令，注册 `/api/app-packager/{state,init,doctor,job,job/log,job/kill}` 六条同源路由；`app_packager_check` 走引擎的 `check <平台> [项目]` 子命令（裸平台参数在引擎里意味着打包），`app_packager_build` 走打包。没有 Web 服务的 profile 里不出现面板，四个工具照常可用。
- 引擎目录即 `$PIPELINE_ROOT`：npm 分发层默认把它放在插件自己的目录里（`<插件目录>/home`），可用 `APP_PACKAGER_HOME` 或 `app-packager --dir <路径>` 覆盖；老版本留下的 `~/AppPackager` 会在第一次解析时被改名搬进新位置（改名不复制，几 GB 的 SDK 也瞬间就位，且只搬真的是引擎目录的那种），跨卷搬不动时保留原目录并把提示带回面板。首次运行把包内 `engine/` 复制到该目录；升级只更新引擎文件，`config/settings.local.env` 等 `*.local.env`、`config/projects/*.env`、`certificates/`、`signing/`、`sdk/`、`packages/`、`logs/`、`workspaces/` 一律保留。npm 打包会丢掉包内的 `.gitignore`，因此首次物化时会补写一份同等规则（忽略本地配置、证书、SDK、产物）的 `.gitignore`，避免用户把引擎目录纳入 Git 时误提交密钥。pnpm 打的 tarball 内文件权限一律为 644（`npm pack` 才保留 755），所以物化时对 `.command`/`.sh` 强制补回 755，保证用户拿到的 `打包工具.command`、`初始化.command`、`一键打包.command` 仍可在访达中双击执行。
- 命令行：`app-packager <命令>`。`init` / `doctor` / `list` / `env` 为 Node 实现（Windows 也可用）；`check` / `build` / `run` 以及以 `ios` / `android` / `harmony` / `all` 开头时透传给引擎，参数与第 6 节完全一致。
- 跨平台运行：macOS/Linux 用系统 bash；Windows 依次探测 `APP_PACKAGER_BASH`、`%ProgramFiles%\Git\bin\bash.exe`、`%ProgramFiles(x86)%\Git\bin\bash.exe`、`%LOCALAPPDATA%\Programs\Git\bin\bash.exe`、`PATH` 上的 `bash.exe`，再回退 `wsl.exe -e bash`（路径用 `wslpath -a` 转换）。iOS 打包仍只能在 macOS 上完成。
- 引擎调用约定不变：父进程设置 `PIPELINE_ROOT` 与 `PROJECT_SEARCH_ROOTS`（默认引擎目录的父目录，多个用 `:` 连接），工作目录为引擎目录。非交互调用必须丢弃标准输入，否则引擎结尾的 `按回车退出...` 会挂住子进程；只有交互式初始化向导才继承 stdin。
- 相关文档：`docs/zh-CN/publishing.md`（npm 发布与 awesome-dsh-plugin 市场上架）、`docs/zh-CN/windows.md`（Windows/Linux 的 bash 桥接与配置要点）、`docs/zh-CN/architecture.md`（分层与数据流）；每份都有 `docs/en/` 英文版。仓库级协作规范见根目录 `AGENTS.md` 与 `CONTRIBUTING.md`。

## 2. 项目读取机制

项目没有写死在代码中，运行时扫描：

```text
config/projects/*.env
```

模板：

```text
config/projects/project.env.example
```

初始化时自动读取项目：

1. 运行 `初始化.command`。
2. 工具扫描 AppPackager 同级目录，识别以下两种结构：
   - `manifest.json + pages.json`
   - `src/manifest.json + src/pages.json`
3. 自动读取 `name`、`appid`、Android `applicationId`，并尝试按 Bundle ID 匹配 `certificates/iOS/` 中已有的 `.mobileprovision`。
4. 自动生成 `config/projects/<项目ID>.env`，项目 ID 默认使用项目目录名。
5. 菜单启动时会对同级目录再做一次静默补扫描，初始化后新增的同级项目也会自动注册。

如果项目不在同级目录，初始化时可以选择输入任意绝对路径；也可以手动复制模板：

```bash
cp config/projects/project.env.example config/projects/my-project.env
```

手动配置示例：

```bash
PROJECT_ID="my-project"
SOURCE_DIR="/absolute/path/to/uni-app-x-project"
HX_PROJECT_NAME="my-project-build"
EXPECTED_BUNDLE_ID="com.example.myapp"
PROFILE_FILE="$PIPELINE_ROOT/signing/current/my-project.mobileprovision"
IOS_ENABLED="true"
ANDROID_ENABLED="true"
# 可选：Android release keystore 配置
# ANDROID_KEYSTORE_PROPERTIES="$PIPELINE_ROOT/certificates/Android/my-project/keystore.properties"
HARMONY_ENABLED="true"
```

`config/projects/*.env` 是本地生成配置。项目目录移动后，重新运行初始化或在菜单中检查项目状态即可发现路径变化。根目录布局和 `src/` 布局在注册、资源处理、权限、版本和签名阶段使用同一套路径解析。

`config/projects/*.env` 已加入 `.gitignore`，不会上传到 GitHub。

选择“指定项目”时，菜单会动态列出当前平台可打包项目，并显示项目名称、平台开关和源码地址，可输入编号或项目 ID。选择完成后，只检查该项目实际启用的平台，未启用平台不再阻断打包。

环境预检通过后，菜单会询问是否上传安装包，并以列表展示当前启用的上传平台；可输入一个编号、多个编号（例如 `1,2`）或直接回车跳过。上传选择对本次打包的多个项目和多个平台生效，每个安装包归档完成后立即分别上传。

“全部项目”操作仍按平台执行环境预检：

| 选择 | 预检内容 |
| --- | --- |
| iOS 指定项目 / 全部项目 | HBuilderX CLI 服务、Xcode 和 Command Line Tools |
| Android 指定项目 / 全部项目 | HBuilderX CLI 服务、Android SDK、JDK、Gradle 实际启动、apksigner、zipalign |
| HarmonyOS 指定项目 / 全部项目 | HBuilderX CLI 服务、DevEco Studio、hvigor、ohpm、HarmonyOS Runtime |
| iOS + Android | 依次检查上述两套环境 |
| iOS + Android + HarmonyOS | 依次检查三套环境 |
| 初始化、SDK、证书、诊断、退出 | 不检查打包工具链 |

Xcode、Android Studio、DevEco Studio 的 GUI 窗口不是当前本地构建的必要条件，因此不要求保持窗口打开；对应命令行工具和 SDK 必须可用。

命令行直接执行 `打包工具.command ios ...`、`android ...` 或 `all ...` 时也会使用同一套平台预检；`list`、`check`、`diagnose` 不触发构建环境预检。批量构建遇到首个失败会立即停止；批量检查会执行完当前检查范围，并在任一项目失败时返回非 0 退出码。

如果当前平台没有可打包项目，工具会先进入项目读取流程：

1. 自动扫描 AppPackager 同级目录。
2. 手动输入 uni-app x 项目绝对路径。
3. 输出读取后的项目清单和源码地址。
4. 返回打包菜单，由用户重新选择打包操作。

`register <目录...>` 用同一套注册逻辑完成上面第 2 步：目录本身是 uni-app x 项目就直接登记，否则扫描它的下一层；不触发平台预检、不等待回车，因此脚本和 Harness 插件面板可以直接调用它写 `config/projects/<id>.env`。

退出方式：

- 直接按回车
- 输入 `0`
- 输入 `16`

## 5.1 初始化/修复打包环境

双击 `初始化.command`，或在主菜单选择 `13`。

SDK 文件还可以直接放入 `sdk/` 根目录，然后双击 `sdk/处理SDK.command`，或在主菜单选择 `14`。

初始化步骤：

1. 检测 HBuilderX 安装和版本。
2. 检测 Xcode、Android Studio、DevEco Studio。
3. 根据 HBuilderX 版本匹配 Android/iOS SDK 系列。
4. 打开官方 SDK 下载页并列出官方下载入口。
5. 支持输入本地压缩包路径或直接 URL，自动解压并导入 `sdk/`。
6. 检测到 DevEco Studio 时，可选用 `ohpm` 安装 HarmonyOS runtime。
7. 检测 Python、Node、Gradle、Android SDK、Xcode Command Line Tools、Keychain 等依赖。
8. 导入或更新证书：可传入证书来源目录，也可以直接扫描 `certificates/` 下的来源目录；来源文件只复制，不移动、不删除。
9. 刷新已注册项目的 iOS Profile 路径，然后自动扫描同级目录并注册本地 uni-app x 项目；未发现时提示放置位置或输入绝对路径。
10. 确保 `config/upload.local.env`、`config/parallel.local.env` 存在，并生成 `config/settings.local.env` 和 `config/init.local.env`。

说明：

- 初始化向导支持输入本地压缩包路径或直接 URL。
- `sdk/处理SDK.command` 会递归扫描 `sdk/` 中 `.zip`、`.tar.gz`、`.tgz`、`.har` 和已解压 SDK 目录。
- SDK 类型识别优先匹配 Android、HarmonyOS 专属文件名，再匹配 iOS/UniAppX，避免 `UniAppX-Android@...`、`UniAppX-HarmonyOS@...` 被误判为 iOS。
- 默认保留根目录原始压缩包和 `sdk/_processed/` 备份；需要自动清理时可设置 `KEEP_SDK_ARCHIVES=false`。
- 百度网盘未完成的 `.downloading` / `.baiduyun.p.downloading` 文件会被单独提示，不会误处理。
- 旧版 iOS `HBuilder-Hello` SDK 可被识别，但当前 AppPackager 分包流程需要 `UniAppX-iOS@<版本>`，并检查是否包含 `UniAppXDemo.xcodeproj`。
- 导入后会归位到 `sdk/iOS/`、`sdk/Android/`、`sdk/HarmonyOS/`。
- Android/iOS 官方 SDK 当前主要通过百度网盘、和彩云等官方渠道分发，初始化工具会打开官方页面并列出下载入口。
- HarmonyOS uni-app x SDK 通过 DevEco 的 `ohpm` 依赖安装：
  `@dcloudio/uni-app-x-runtime: "<HBuilderX系列>.*"`。
- 所有机器本地的 SDK 路径、项目路径和初始化状态都写入 Git 忽略文件。

上面这组打包选项（`--full-permission` / `--no-full-permission`、`--package-kind`、`--profile`、`--set`）对 `check` 同样有效：`check ios <项目ID> --package-kind appstore` 就是“按正式包接线检查一遍”，描述文件缺失或类型不符会在这里先报出来，不必等打包。

`sdk` 是 SDK 诊断与安装入口，四种用法（`status` / `urls` / `install <平台|all> [--yes] [--file <压缩包>]` / `process`）都只读使用者的项目，只在引擎目录内写 `sdk/` 与 `config/settings.local.env`：

- `sdk status` 输出 JSON（`hbuilderx` 的路径/版本/系列、`series`、`platforms[]` 的 `label`/`state`/`dir`/`page`/`direct`/`hint`、`archives[]`、`incompleteDownloads`、`settingsFile`）。`state` 只有三种：`ready`（目录齐备）、`mismatch`（有 SDK 但不是当前 HBuilderX 系列）、`missing`（没有）。`direct` 只在 iOS 上出现——它的压缩包名由系列唯一决定（`UniAppX-iOS@<系列>.zip`）；Android 的文件名带构建号，只能从官方页解析，因此只给 `page` 与 `hint`；HarmonyOS 没有压缩包，走 ohpm 装 runtime，所以 `hint` 给的是 ohpm 包名。
- `sdk urls` 是同一份信息的人读版，逐平台打印官方下载页、官方直链或 ohpm 包名，适合直接照着下。它与 `sdk status` 一样先解析本机 HBuilderX，所以开头的「版本」「SDK 系列」给的是真实版本号（没装 HBuilderX 时才写「未知」），不会出现装好了却显示版本未知的情况。HarmonyOS 一行的标签写作 `ohpm 包名:` 并注明来自 DevEco 的 ohpm 仓库——这个 runtime 不在 npm 上，`npm view` 会 404，写清楚免得照着 npm 去找。
- `sdk install` 按平台下载（`curl -L --fail`，带进度）并复用 `import_sdk_archive`：解压、归位到 `sdk/<平台>/<系列>`、写出 `config/settings.local.env` 的 SDK 路径。`--yes` 跳过交互确认（面板与脚本用）；`--file <压缩包>` 用本机已有的包，适合下载页访问不了或带宽受限的机器；`all` 依次处理三个平台。平台没有确定性直链时不会瞎猜，而是打印官方下载页并返回非 0。已经 `ready` 的平台会打印「已就绪，跳过」并直接略过，所以「一键配置全部」可以反复点、不会重复下载几百 MB（`--file` 是显式意图，照常执行）。判定以平台**真的就绪**为准：使用者拒绝安装、DevEco ohpm 缺失、下载或解压失败都会返回非 0，不会出现什么都没装上却报「SDK 配置完成」。写进 `config/settings.local.env` 的 SDK 路径若在引擎目录内，会写成 `"$PIPELINE_ROOT/..."` 形式：引擎目录整体挪走（例如从 `~/AppPackager` 搬进插件目录）后仍然指向同一份 SDK，不会因为绝对路径过期而重新下载。
- `sdk process` 与 `sdk/处理SDK.command` 同一条代码路径：递归扫描 `sdk/` 下的 `.zip`、`.tar.gz`、`.tgz`、`.har` 与已解压目录并归位。
- 判定就绪只看真正能用的产物：HarmonyOS 必须存在 `oh_modules/@dcloudio/uni-app-x-runtime`（或 vapor 对应包，或目录里的 `*.har`）。旧逻辑把安装器**先写出来**的 `oh-package.json5` 当作就绪证据，`ohpm install` 中途失败也会被当成装好了；现在这条假阳性已去掉。

## 7. HBuilderX 静默编译流程

HBuilderX 仍然需要作为本机编译服务运行，但不再执行：

```text
project open
project close
```

实际使用：

```bash
/Applications/HBuilderX.app/Contents/MacOS/cli publish app-ios   --type appResource   --project "<隔离工作区绝对路径>"

/Applications/HBuilderX.app/Contents/MacOS/cli publish app-android   --type appResource   --project "<隔离工作区绝对路径>"
```

HBuilderX 支持通过绝对路径创建临时 CLI 工作区，因此：

- 不在项目列表中增加 `*-build`。
- 不切换当前编辑器窗口。
- 不影响正在编辑的其他 HBuilderX 项目。
- 构建结束后无需关闭编辑器项目。

如果 HBuilderX 已经在运行，流水线直接复用；如果未运行，流水线会用 `cli open` 启动一次编译服务。

## 7.1 并行构建调度

多项目、多平台打包时，AppPackager 使用统一调度器并行执行构建任务，并对重型工具做全局闸门控制：

- 总并发任务数：按 CPU 和内存自动计算，默认最多 3。
- iOS/Android：默认最多 2 个平台任务同时执行。
- HarmonyOS：默认最多 2 个流水线任务，但 HBuilderX 实际编译阶段仍只允许 1 个任务。
- 工作区准备：默认最多 2 个任务同时复制/准备隔离工作区。
- 上传：默认最多 2 个任务同时上传。
- HBuilderX：全局默认最多 1 个 CLI 任务。
- Xcode：全局默认最多 1 个 Archive/导出任务。
- Gradle：全局默认最多 1 个构建进程，单进程默认最多 2 个 worker。
- 每个任务使用独立的“项目 + 平台”工作区、项目锁、运行日志和 HBuilderX/Xcode/Gradle 工具锁。
- 任务在流水线中分段推进：工作区准备、HBuilderX 资源/打包、Xcode/Gradle/Hvigor 本地构建、归档、上传。工作区准备和上传可以并行，但关键编辑器/构建器仍串行。
- 每个平台有独立工作区：
  `workspaces/<项目ID>/<HX项目名>-ios|android|harmony`。
- 并行任务默认捕获各自控制台输出；失败时自动输出对应任务的日志尾部。
- 并行任务使用非交互模式，缺少 API Key/P12 密码时只记录上传失败，不阻塞或等待输入；上传失败不影响打包。
- `PARALLEL_FAIL_FAST=false` 时继续执行其他任务，最后汇总失败；设为 `true` 时不再启动后续任务。

配置文件：

```text
config/parallel.env
config/parallel.local.env
```

常用配置：

```bash
PARALLEL_BUILD_ENABLED="true"
PARALLEL_AUTO_TUNE="true"
PARALLEL_MAX_JOBS="auto"
PARALLEL_MAX_IOS_JOBS="2"
PARALLEL_MAX_ANDROID_JOBS="2"
PARALLEL_MAX_HARMONY_JOBS="2"
PARALLEL_MAX_HBULDERX_JOBS="1"
PARALLEL_MAX_XCODE_JOBS="1"
PARALLEL_MAX_GRADLE_JOBS="1"
PARALLEL_MAX_PREPARE_JOBS="2"
PARALLEL_MAX_UPLOAD_JOBS="2"
PARALLEL_GRADLE_WORKERS="2"
PARALLEL_AUTO_JOBS_MAX="3"
PARALLEL_RESERVED_CPU_CORES="1"
PARALLEL_MEMORY_PER_JOB_MB="4096"
PARALLEL_QUEUE_REFRESH_SECONDS="1"
PARALLEL_LIVE_QUEUE_DISPLAY="true"
```

终端队列会按平台分块显示：`进行中`、`排队中`、`成功`、`失败`，并显示进度条和当前阶段说明。队列状态文件位于每次并行构建的 `logs/parallel/<时间>/status/`。

示例：

```text

进行中 2    排队中 2    成功 1    失败 0

[Android]  运行 1/3  成功 1  失败 0
  01  uni-platform-app       进行中  [██████░░░░]  60%  生成 Android 资源
  02  uni-platform-customer  等待中  [██████░░░░]  35%  等待 HBuilderX 名额
  03  another-android-app    成功    [██████████] 100%  已完成

[iOS]
  01  uni-platform-app       进行中  [███████░░░]  70%  执行 Xcode Archive
```

默认自动调优逻辑：内存低于 8GB 时总并发 1；低于 32GB 时最多 2；32GB 及以上时最多 3，并同步受 CPU 核心数和 `PARALLEL_AUTO_JOBS_MAX` 限制。

默认保守设置的目的是优先保护 HBuilderX 和电脑稳定性；如果机器性能足够，可以只调整 `config/parallel.local.env`，不建议提高 `PARALLEL_MAX_HBULDERX_JOBS`。

## 8. iOS 打包流程

1. 读取 `config/projects/<项目ID>.env` 和项目 `manifest.json`。
2. 复制业务项目到隔离工作区。
3. 仅当对应平台的 `app-ios` / `app-android` 配置中存在图标或启动页时，才使用这些原始配置准备品牌资源；iOS 支持 `splashScreens.storyboard` ZIP 和图片两种形式，未配置时直接使用 uni-app/原生默认资源。
4. 通过 HBuilderX 静默生成 iOS App 资源。
5. 读取当前 `mobileprovision`，自动解析 Bundle ID、Team ID、类型和过期时间。
6. 创建临时 Keychain，导入 p12 和 Apple 证书链。
7. 复制本地 UniAppX iOS SDK 中的 `UniAppXDemo`。
8. 动态扫描并挂载项目中的所有 iOS 自定义 UTS 插件；没有 UTS 时直接跳过，不把插件数量或名称写死。
9. 写入 AppID、Bundle ID、显示名称、channel 和签名配置；entitlements 只保留当前 Profile 明确授权的能力，并合并 `aps-environment`、`keychain-access-groups` 和 `com.apple.developer.*`，同时使用 manifest 中的 associated domains。
10. 执行 `xcodebuild archive`，再导出 IPA。
11. 按插件清单校验自定义 UTS 类和原生 framework/bundle 是否进入 IPA；没有自定义插件时跳过。
12. 复制 IPA 到 `packages/iOS/`，更新 `*-latest.ipa`。
13. 如果本次选择了上传平台，归档完成后由上传统一扩展层按 `build-info.json` 上传；上传失败不影响 IPA 打包结果。
14. 清理临时文件，仅保留最近 5 份构建和日志。

## 9. Android 打包流程

1. 读取项目配置和实际布局下的 `manifest.json`。
2. 复制业务项目到隔离工作区。
3. 当 `FULL_PERMISSION_PROFILE=true` 时，把全量 Android 权限和 iOS 隐私说明合并进隔离副本。
4. 当 `FULL_PERMISSION_PROMPT=true` 时，从合并后的 manifest 提取运行时权限并注入 Android 首次启动申请；不会申请 manifest 未声明的权限。
5. 通过 HBuilderX 静默生成 Android App 资源。
6. 复制 HBuilderX 生成的 Java/Kotlin 和资源到项目原生工程。
7. 修改版本号、applicationId、Gradle 内存、SDK 路径。
8. 如果找到项目级 `keystore.properties`，改写隔离副本的 release signingConfig；密码通过进程环境变量提供给 Gradle，不写入构建文件。
9. 执行 Android Gradle `assembleRelease`，优先离线；缓存不完整时自动联网补齐一次。
10. 使用 `apksigner` 验证签名，使用 `zipalign` 验证 APK 对齐。
11. 复制 APK 到 `packages/Android/`，写入签名模式/指纹，更新 `*-latest.apk`。
12. 如果本次选择了上传平台，归档完成后由上传扩展层处理；上传失败不影响 APK 打包结果。
13. 仅保留最近 5 份构建和日志。

未配置项目级 release keystore 时，APK 继续使用业务项目自己的签名配置。当前业务项目默认是：

```text
<业务项目>/app-android/app/debug.keystore
```

这种情况下终端结果和 `build-info.json` 会明确标记为项目测试签名。推荐由证书导入器平铺到：

```text
certificates/Android/release.keystore
certificates/Android/keystore.properties
```

导入器会同步改写 properties 中的 `storeFile`。也可以在项目配置中用 `ANDROID_KEYSTORE_PROPERTIES` 指定其他绝对路径。正式发布前必须使用 release keystore。

Android 构建参数在 `config/settings.env` 中控制：`ANDROID_GRADLE_BIN` 指定已验证的 Gradle，`ANDROID_USE_PROJECT_WRAPPER=true` 时优先使用业务项目的 `gradlew`，`ANDROID_AGP_VERSION` 用于保持 AppPackager 已验证的 AGP 组合。最终 APK 必须通过 `apksigner` 和 `zipalign` 校验后才能归档。

## 10. 权限清单

权限策略在 `config/settings.env` 中控制：

```bash
FULL_PERMISSION_PROFILE="true"
FULL_PERMISSION_PROMPT="true"
```

- `FULL_PERMISSION_PROFILE=true`：构建 iOS/Android 资源前，把全量 Android 权限和 iOS 隐私说明合并到隔离构建副本。
- `FULL_PERMISSION_PROMPT=true`：Android 首次启动主动申请最终 manifest 中声明的常用运行时权限；配置未包含的运行时权限不会被请求。
- 关闭后使用业务项目自己的权限配置。
- 单次打包可以用 `--full-permission` / `--no-full-permission` 覆盖这两个开关（两个键一起改），不改 `config/settings.env`：`./打包工具.command ios <项目ID> --no-full-permission`。

### 10.5 证书目录与创建文档

证书统一放在：

```text

├── iOS/
├── Android/
│   └── <项目ID>/

```

处理脚本是一个证书导入器，可以接收任意来源目录：

```bash
./certificates/处理证书.command "/absolute/path/to/cert-dir"
```

双击运行时，会扫描 `certificates/` 根目录及其非平台子目录。脚本按扩展名和同目录上下文匹配平台：

- iOS：`.mobileprovision`、与 mobileprovision 同组的 `.p12`
- Android：`.keystore`、`.jks`、`keystore.properties`
- HarmonyOS：`.p7b`、与 p7b 同组的 `.p12`/`.cer`

来源目录中的证书会被复制到对应平台目录；来源位于 `certificates/` 下时，导入成功后会清理来源目录，最终证书目录只保留 `iOS/`、`Android/`、`HarmonyOS/`、`README.md` 和 `处理证书.command`。目标文件名由证书内容决定：

```text
certificates/iOS/<BundleID>.mobileprovision
certificates/iOS/ios-signing.p12
certificates/Android/release.keystore
certificates/Android/keystore.properties
certificates/HarmonyOS/<BundleName>.release.p7b
certificates/HarmonyOS/<BundleName>.debug.p7b
certificates/HarmonyOS/release.p12
certificates/HarmonyOS/release.cer
certificates/HarmonyOS/dev.cer
certificates/HarmonyOS/material/
```

再次执行时会按内容身份更新同名文件：相同内容不处理；不同内容先备份到 `logs/certificate-history/<时间>/`，再原子替换当前文件。各平台统一按“项目原配置优先，其次平台证书目录，最后 uni-app 默认/提示处理”的顺序读取证书；任何情况下都不修改证书文件内容。

iOS 和 HarmonyOS 都可能使用 `.p12`。p12 必须放入对应平台目录，或在文件名中包含明确的 `ios`、`apple`、`harmony`、`ohos` 关键字；无法判断平台时会列入异常，不会自动混用。缺失或结构不完整时会显示 UniApp 官方创建文档。

官方文档：

- iOS: https://ask.dcloud.net.cn/article/152
- Android: https://ask.dcloud.net.cn/article/35777
- HarmonyOS: https://doc.dcloud.net.cn/uni-app-x/tutorial/runbuild.html#signing-configs

初始化向导和主菜单都会同步检查证书状态。iOS 优先使用项目配置中的 `PROFILE_FILE` 和 `P12_FILE`；项目未提供或文件不存在时，才从 `certificates/iOS/` 按 Bundle ID 匹配 Profile 和同组 p12。两边都不可用时提示运行证书处理，不覆盖项目配置。

Android 优先使用项目自己的非 debug signingConfig 或 `keystore.properties`；项目仍是 debug/无显式配置时，才使用 `certificates/Android/`。两边都没有时保持业务项目原有签名并明确提示测试签名。

HarmonyOS 优先使用项目 `manifest.json` 的 `app-harmony.distribute.signingConfigs`。项目缺配置时，才按 Bundle Name 从 `certificates/HarmonyOS/` 选择 p12/cer/p7b/material，并只在隔离工作区生成 signingConfigs；项目配置和平台证书都没有时，保留 uni-app 默认处理并提示。`material/` 是解密 manifest 加密密码所必需的材料，必须与证书一起原样复制，不修改内容。

## 9.1 HarmonyOS 打包流程

1. 读取项目配置和 `manifest.json` 中的 `app-harmony.distribute.signingConfigs`。
2. 检查 `storeFile`、`certpath`、`profile`、`keyAlias`、`signAlg` 和密码字段，不从其他位置替换这些配置。
3. 如果 signingConfigs 引用文件不存在，只按同名文件从证书来源原样复制到配置路径，不修改文件内容。
4. 普通发布模式在隔离工作区调用 HBuilderX `pack app-harmony`；本地侧载模式调用 HBuilderX `launch app-harmony --buildType debug --compile true`，由 HBuilderX 使用项目 signingConfigs 完成签名。
5. 只接受 `*-signed.hap`；没有 signed HAP 时直接构建失败，不再由 AppPackager 二次签名。
6. 将 signed HAP 复制到 `packages/HarmonyOS/`，更新 `*-latest.hap`。
7. 测试侧载模式不进入蒲公英 HarmonyOS HAP 上传流程；如后续关闭 TEMP-10021，并由项目提供满足发布要求的签名配置，再按上传扩展层规则处理。
8. 仅保留最近 5 份构建和日志。

HarmonyOS 证书文件只读使用，不生成、不重写、不拼接证书链。

### 9.1.1 [TEMP-10021] 临时安装补丁

该补丁默认关闭，正常打包使用 `release` signingConfig：

```bash
HARMONY_TEMP_FORCE_INSTALL_SIGNING="false"
```

开启后的行为：

- 未选择上传平台时，调用 HBuilderX `launch app-harmony --buildType debug --compile true` 生成真机可安装的 `buildMode=debug` HAP。
- 直接使用项目原始 `app-harmony.distribute.signingConfigs.default`，不把 debug 配置映射到 release，也不修改源项目 `manifest.json`。
- 不修改证书文件内容。
- 产物按安装包处理，更新 `*-latest-install.hap`。
- 选择蒲公英等上传平台时跳过测试补丁，继续使用项目原有 `release` signingConfig 和 `pack app-harmony` 发布流程。
- `--harmony-debug` 可显式生成 debug 侧载包，不依赖本配置项。
- `build-info.json` 写入：
  ```json
  {
    "temporary_patch": "TEMP-10021"
  }
  ```

切换方式：

1. 正常发布打包保持 `HARMONY_TEMP_FORCE_INSTALL_SIGNING="false"`。
2. 临时测试侧载可改为 `true`，或直接使用 `--harmony-debug`。
3. 蒲公英发布必须使用 `release + internaltesting` Profile。

注意：蒲公英 HarmonyOS 应用分发要求发布证书 P12，并匹配“指定设备发布”Profile；若项目原有 `release` Profile 是 AppGallery 类型且不包含测试设备 UDID，不能用于蒲公英，需要重新申请指定设备发布 Profile。

相关代码位置：

```text

lib/common.sh: activate_harmony_temporary_install_patch
lib/common.sh: build_harmony_hap
```

### 9.1.2 [PGYER-17700015] 蒲公英 HAP 兼容模式

选择蒲公英上传时，HarmonyOS 打包默认使用以下组合：

- 签名配置：项目 `release` signingConfig
- Profile：`release + internaltesting`
- 设备：Profile 中必须包含测试设备 UDID
- HAP 构建模式：HBuilderX release（`debug=false/buildMode=release`）
- HAP `targetAPIVersion`：`5.0.1(13)`，与蒲公英生成的安装 manifest 保持一致
- `versionCode`：可按项目配置 `HARMONY_VERSION_CODE`，用于覆盖已安装版本配置不同导致的 `17700015`

构建结束后会执行硬校验：HAP 必须为 release、目标 API 必须匹配、Profile 必须为 `release/internaltesting`、设备数必须大于 0、配置了版本号时必须匹配；任一条件不满足会直接失败。

目标 API 版本由 `HARMONY_PGYER_TARGET_SDK_VERSION` 控制。`HARMONY_PGYER_DEBUGGABLE=true` 可切换为 debug HAP 兼容构建，但默认推荐 release HAP。

- `config/upload.env`：平台注册、支持产物、接口地址、超时和轮询参数，可提交。当前已预留蒲公英、App Store、华为应用市场、小米应用市场、应用宝五类配置。
- `config/upload.local.env`：各平台 API Key、Token、证书密码等本机敏感配置，不提交。
- `config/upload.local.env.example`：本机配置模板；初始化向导会在缺失时自动复制为 `config/upload.local.env`。
- 当前已实现 provider：蒲公英。
- 已预留但默认关闭：App Store、华为应用市场、小米应用市场、应用宝；在对应 provider 脚本实现前不会出现在上传菜单。
- 已兼容原 `uni-platform-app/scripts/ios-package/env/adhoc.env` 中的 `PGYER_API_KEY`、`PGYER_UPDATE_DESCRIPTION`，未复制企业微信、Web 构建、Docker 构建/推送逻辑。

当前注册的上传平台：

```bash
UPLOAD_PLATFORM_IDS="pgyer appstore huawei xiaomi yingyongbao"
```

其中只有蒲公英默认启用：

```bash
UPLOAD_PLATFORM_pgyer_NAME="蒲公英"
UPLOAD_PLATFORM_pgyer_ENABLED="true"
UPLOAD_PLATFORM_pgyer_PLATFORMS="ios android harmony"

```

App Store、华为应用市场、小米应用市场、应用宝的配置和本机凭据字段已经预留，但 `ENABLED=false`，不会出现在上传菜单中，直到对应 provider 脚本完成实现。

执行方式：

1. 菜单选择打包操作和项目。
2. 环境预检通过后，列表选择上传平台，可多选。
3. 打包流程正常执行并写入 `build-info.json`。
4. 每个产物归档完成后，上传扩展层读取 `build-info.json`。
5. 蒲公英支持 APK、IPA 和 HAP；HAP 会额外上传 P12 证书和密码。
6. 上传结果写回 `build-info.json` 的 `uploads` 字段。
7. 上传日志和响应保存在 `logs/uploads/<平台>/`。
8. 上传失败只输出警告，不回滚安装包，也不改变打包成功状态。
9. 终端产物地址规则：未选择上传平台时，列出成功产物的实际文件地址；只要选择了一个或多个上传平台，就不再展开产物文件地址，只显示上传结果。并行队列模式也会统一按此规则处理。

蒲公英 API Key 查找顺序：

1. 环境变量 `PGYER_API_KEY`。
2. macOS Keychain，默认 service：`app-packager-pgyer`。
3. 交互终端中输入后可选择保存到 Keychain。

手动保存 Keychain：

```bash
security add-generic-password -U -a "$USER" -s app-packager-pgyer -w
```

推荐写入本机忽略提交的 `config/upload.local.env`：

```bash
PGYER_API_KEY="..."
```

可选蒲公英参数：

```bash
PGYER_BUILD_INSTALL_TYPE=""
PGYER_BUILD_PASSWORD=""
PGYER_BUILD_UPDATE_DESCRIPTION=""
# 兼容原 uni-platform-app 的版本说明字段，优先于 PGYER_BUILD_UPDATE_DESCRIPTION
PGYER_UPDATE_DESCRIPTION=""
PGYER_LEGACY_UPLOAD_URL="https://upload.pgyer.com/apiv2/app/upload"
PGYER_UPLOAD_TIMEOUT_SECONDS="600"
PGYER_POLL_TIMEOUT_SECONDS="300"
PGYER_POLL_INTERVAL_SECONDS="3"
```

HarmonyOS HAP 额外需要 P12 明文密码。可使用环境变量或 Keychain，不能使用 `manifest.json` 中 HBuilderX 加密后的 `storePassword`：

```bash
PGYER_HARMONY_P12_PASSWORD="..."
```

也可保存到 Keychain：

```bash
security add-generic-password -U -a "$USER" -s app-packager-pgyer-harmony-p12 -w
```

上传器会按顺序尝试 `PGYER_HARMONY_P12_PASSWORD`、`HARMONY_P12_PASSWORD`、`app-packager-pgyer-harmony-p12` Keychain、`anjuyi-harmony-p12` Keychain；仍无密码时可在交互终端输入。

HarmonyOS HAP 通过蒲公英内测分发的签名要求：

1. `.p12` 必须是发布证书，不能使用调试证书。
2. `.p7b` 必须是“指定设备发布”Profile，并且包含测试设备 UDID。
3. `.hap` 必须使用上述 `.p12` 和 `.p7b` 签名。
4. 上传到蒲公英的 `.p12` 必须与签署 `.hap` 的 `.p12` 完全一致。
5. `--harmony-debug` 主要用于本地侧载安装，不应作为蒲公英正式内测分发的签名配置。

AppPackager 会在上传前检查 `harmony_profile_type` 和 `harmony_profile_device_count`。如果 Profile 是 debug，或设备数量为 0，会明确提示更新项目 `signingConfigs`，但不会修改或替换证书。

初始化向导会确保 `config/upload.local.env` 存在，并保留已有的 `PGYER_*` / `UPLOAD_*` / HarmonyOS P12 本机配置。

蒲公英官方文档：

- HarmonyOS 内测分发：https://www.pgyer.com/doc/view/harmonyos
- API 上传与发布：https://www.pgyer.com/doc/view/api_upload

新增上传平台时，新增独立 provider 脚本，并在 `config/upload.env` 登记 `UPLOAD_PLATFORM_<ID>_NAME`、`_ENABLED`、`_PLATFORMS`、`_SCRIPT`、`_FUNCTION` 后加入 `UPLOAD_PLATFORM_IDS`。平台 ID 只使用字母、数字和下划线。不要修改各平台打包函数；打包函数只调用统一扩展入口 `run_post_build_uploads`。
